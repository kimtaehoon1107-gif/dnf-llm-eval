# 던파 업데이트 기반 LLM 평가 데이터셋 구축 진행 보고서

작성일: 2026-05-27

## 1. 프로젝트 목적

본 프로젝트는 넥슨 게임 도메인 LLM 평가 어시스턴트 인턴 지원을 준비하기 위해, 실제 던전앤파이터 업데이트 문서를 수집하고 이를 기반으로 LLM 응답 품질을 평가할 수 있는 벤치마크 데이터셋을 구축하는 것을 목표로 한다.

단순히 웹 문서를 모으는 것이 아니라, 게임 도메인 문서를 LLM 평가 관점에서 구조화하고, 질문-정답-근거-채점 기준까지 연결하는 작은 평가 파이프라인을 만드는 것이 핵심이다.

## 2. 현재까지 완료한 작업

### 2.1 프로젝트 구조 구성

현재 프로젝트는 다음 구조로 정리되어 있다.

```text
dnf-llm-eval/
  data/
    raw_html/
    processed_md/
    metadata.csv
    discovered_update_urls.csv
  scripts/
    collect_dnf_updates_selenium.py
  questions/
  eval/
  report/
```

각 폴더의 역할은 다음과 같다.

- `scripts/`: 데이터 수집 자동화 코드 보관
- `data/raw_html/`: 원본 HTML 저장
- `data/processed_md/`: LLM 평가에 사용할 Markdown 문서 저장
- `data/metadata.csv`: 문서별 제목, 유형, URL, 저장 경로, 수집 상태 관리
- `questions/`: 평가 질문 데이터셋 저장 예정
- `eval/`: 평가 기준표와 채점 결과 저장 예정
- `report/`: 프로젝트 설명 및 결과 보고서 저장

### 2.2 던파 업데이트 목록 구조 분석

초기에는 업데이트 목록에서 일반적인 링크 구조를 찾으려 했다.

```html
<a href="/community/news/update/2927399">...</a>
```

하지만 실제 던파 업데이트 목록은 일반적인 `a href` 구조가 아니라, 다음처럼 `li.title` 태그의 `data-no` 속성에 상세 글 번호가 들어 있었다.

```html
<li class="category">퍼스트서버</li>
<li class="title" data-no="2927399">5/20(수) 퍼스트 서버 업데이트 안내</li>
<li class="date">2026.05.20</li>
```

따라서 기존 `requests + BeautifulSoup` 방식만으로는 상세 링크를 안정적으로 찾기 어려웠고, Selenium으로 렌더링된 목록 HTML을 가져온 뒤 `data-no`와 `data-url`을 파싱하는 방식으로 변경했다.

### 2.3 Selenium 기반 수집기 실행 성공

현재 `scripts/collect_dnf_updates_selenium.py`를 실행하여 최신 업데이트 문서 5개를 수집하는 데 성공했다.

생성된 Markdown 문서는 다음과 같다.

```text
DOC-01_5_28(목)_정기점검_업데이트_안내.md
DOC-02_5_20(수)_퍼스트_서버_업데이트_안내.md
DOC-03_5_21(목)_정기점검_업데이트_안내.md
DOC-04_최후의_과업_업데이트.md
DOC-05_5_6(수)_퍼스트_서버_업데이트_안내.md
```

현재 수집기는 다음 기능을 수행한다.

- 업데이트 목록 페이지 접속
- 렌더링된 HTML 저장
- `article.board_list.news_list` 영역 파싱
- 각 공지의 카테고리, 제목, 날짜, 상세 URL 추출
- 상세 페이지 HTML 저장
- 본문 텍스트를 Markdown으로 변환
- 문서 메타데이터를 CSV로 저장

## 3. 현재 발견된 문제

### 3.1 한글 인코딩 깨짐 문제

수집된 Markdown 파일을 확인한 결과, 일부 본문과 메타데이터에서 한글이 깨져 있다.

예시는 다음과 같다.

```text
# 5/28(紐? ?뺢린?먭? ?낅뜲?댄듃 ?덈궡
?꾪룷移쇰┰??: ?덊떚?붾컮??...
```

이는 상세 페이지 HTML을 가져올 때 응답 인코딩이 정확히 처리되지 않았기 때문으로 보인다. 현재 코드에서는 `response.apparent_encoding`을 사용하고 있는데, 일부 페이지에서 이 값이 잘못 추론될 수 있다.

이 문제를 해결하지 않으면 LLM 평가 질문 생성, 정답 추출, 근거 문장 연결이 모두 부정확해질 수 있으므로 다음 단계에서 가장 먼저 수정해야 한다.

### 3.2 날짜 추출 오류

`metadata.csv`를 확인한 결과, `DOC-01`의 `posted_date`가 날짜가 아니라 `15:00`으로 저장되어 있다.

```text
DOC-01,regular_update,일반,15:00,5/28(목) 정기점검 업데이트 안내,...
```

목록 페이지에서 날짜 영역 대신 시간 문자열이 잡힌 것으로 보인다. 문서 정렬과 기간 분석에는 큰 문제가 될 수 있으므로, 날짜 추출 로직도 보정이 필요하다.

### 3.3 본문 추출 범위 검증 필요

현재는 `div.operation_guide`, `div.bd_viewcont`, `article.bview_btarea`, `section.content.news` 중 하나를 본문 후보로 선택한다.

다만 실제 문서별 HTML 구조가 조금씩 다를 수 있으므로, 다음 항목을 확인해야 한다.

- 메뉴, 푸터, 로그인 문구가 섞이지 않았는지
- 업데이트 본문이 중간에 잘리지 않았는지
- 표 형태의 아이템 정보가 읽을 수 있는 텍스트로 보존되는지
- 대규모 업데이트 페이지와 일반 공지 페이지의 구조 차이를 처리하는지

## 4. 다음 작업 방향

### 4.1 1단계: 수집 품질 안정화

가장 먼저 수집된 문서가 평가 데이터로 쓸 수 있을 만큼 깨끗한지 확인해야 한다.

작업 항목은 다음과 같다.

1. 상세 페이지 인코딩 처리 수정
2. 기존 Markdown 재생성
3. `metadata.csv`의 제목, 카테고리, 날짜 값 검증
4. 본문 추출 범위 검증
5. 문서별 품질 체크 결과 기록

완료 기준은 다음과 같다.

- Markdown 파일에서 한글이 정상 출력된다.
- 제목, 카테고리, 날짜가 사람이 읽을 수 있는 형태로 저장된다.
- 본문에 불필요한 페이지 UI 텍스트가 거의 없다.
- 원문 의미가 훼손되지 않는다.

### 4.2 2단계: 문서 요약 및 정보 구조화

수집 문서가 정리되면 각 문서를 LLM 평가용으로 구조화한다.

문서별로 다음 정보를 정리한다.

- 문서 ID
- 문서 유형
- 핵심 업데이트 요약
- 주요 변경점
- 아이템, 던전, 보상, 시스템 등 주요 엔티티
- 사용자가 질문할 만한 포인트
- 답변 근거가 되는 문장

이 단계의 산출물은 `data/document_summaries.csv` 또는 `report/document_summary.md` 형태가 적합하다.

### 4.3 3단계: 벤치마크 질문 생성

문서 내용을 바탕으로 LLM 평가 질문을 만든다. 질문은 단순 정보 검색형만 만들지 않고, 실제 유저가 할 법한 질문으로 구성한다.

질문 유형은 다음처럼 나눌 수 있다.

- 사실 확인형: 특정 아이템, 날짜, 보상, 조건을 묻는 질문
- 비교형: 퍼스트 서버와 정기점검 업데이트의 차이를 묻는 질문
- 절차형: 특정 콘텐츠 참여 방법이나 보상 획득 방식을 묻는 질문
- 조건 판단형: 특정 상황에서 보상을 받을 수 있는지 묻는 질문
- 요약형: 긴 업데이트 내용을 사용자 관점에서 요약하게 하는 질문
- 근거 요구형: 답변에 사용한 원문 근거를 함께 제시하게 하는 질문

초기 목표는 문서 5개 기준 20~30개 질문을 만드는 것이다.

### 4.4 4단계: 정답 및 근거 문장 작성

각 질문에는 반드시 기준 정답과 근거 문장을 붙인다.

추천 데이터 구조는 다음과 같다.

```text
question_id
doc_id
question_type
question
gold_answer
evidence
difficulty
expected_behavior
```

이렇게 구성하면 단순 질문 목록이 아니라 실제 평가 가능한 벤치마크가 된다.

### 4.5 5단계: LLM 응답 평가 기준 설계

지원 공고의 주요 업무와 직접 연결되는 부분이다.

평가 기준은 다음 축으로 설계한다.

| 평가 항목 | 설명 | 점수 |
|---|---|---|
| 정확성 | 원문 내용과 답변이 일치하는가 | 0~3 |
| 근거성 | 답변이 문서 근거를 기반으로 하는가 | 0~3 |
| 완전성 | 질문에 필요한 정보를 빠짐없이 포함했는가 | 0~3 |
| 사용자 의도 적합성 | 실제 유저 질문 의도에 맞게 답했는가 | 0~3 |
| 환각 여부 | 문서에 없는 내용을 만들어내지 않았는가 | 0~3 |
| 표현 품질 | 게임 유저가 이해하기 쉽게 설명했는가 | 0~3 |

최종 점수는 18점 만점으로 두고, 필요하면 항목별 가중치를 부여한다.

### 4.6 6단계: 샘플 평가 실행

질문 5~10개를 골라 실제 LLM 응답을 평가한다.

평가 결과에는 다음을 포함한다.

- 질문
- 기준 정답
- 모델 응답
- 항목별 점수
- 감점 사유
- 개선 의견

이 단계까지 완료하면 지원서나 면접에서 “LLM 평가를 직접 설계하고 수행해 보았다”는 근거로 활용할 수 있다.

7. 평가 루브릭 작성
8. 샘플 모델 응답 평가
9. 최종 보고서 및 자기소개서 연결 문장 정리

## 6. 포트폴리오/지원서에 연결할 수 있는 포인트

이 프로젝트는 지원 공고의 주요 업무와 다음처럼 연결된다.

| 공고 주요 업무 | 본 프로젝트 대응 내용 |
|---|---|
| 게임 도메인 특화 LLM 벤치마크 구성 | 던파 업데이트 문서 기반 질문 데이터셋 구축 |
| 평가 지표 및 기준 개발 | 정확성, 근거성, 완전성, 환각 여부 등 루브릭 설계 |
| LLM 응답 품질 평가 | 기준 정답과 근거 문장 기반 정량/정성 평가 |
| 결과 분석 및 공유 | 평가 결과 보고서와 개선 의견 작성 |

지원서에서는 다음처럼 표현할 수 있다.

```text
던전앤파이터 업데이트 공지를 수집하여 게임 도메인 LLM 평가용 벤치마크를 직접 구성했습니다.
공지 목록의 HTML 구조를 분석해 Selenium 기반 수집 파이프라인을 만들었고, 수집한 문서를 Markdown과 메타데이터로 정리했습니다.
이후 문서별 핵심 정보를 바탕으로 유저 질문 시나리오, 기준 정답, 근거 문장, 평가 루브릭을 설계해 LLM 응답의 정확성, 근거성, 환각 여부를 평가하는 방식으로 확장하고 있습니다.
```

## 7. 다음 즉시 실행할 작업

다음 작업은 수집 코드의 인코딩 처리 수정이다.

우선 `fetch_page()` 함수에서 응답 인코딩을 안정적으로 처리하도록 수정하고, 기존 `processed_md`와 `raw_html`을 재생성한다. 그 후 Markdown 파일을 다시 열어 한글이 정상인지 확인한다.

이 작업이 끝나면 질문 생성 단계로 넘어갈 수 있다.
