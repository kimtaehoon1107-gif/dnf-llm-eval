# Automatic Change-Record Extractor Prototype (v1)

작성일: 2026-07-04

## 배경

`heldout_factual_ablation_v1.md`와 로드맵 2번 항목은 손으로 쓴 `source_relation`/`answer_hint`가 dev 문항에만 매칭되고(9/20) held-out에는 하나도 발동하지 않았다(0/25)는 것을 확인했고, 다음 방향으로 "원문 패치노트에서 atomic before/after/field record를 자동 추출하는 extractor"를 제안했다. 이 문서는 그 최소 프로토타입 결과다.

스크립트: `scripts/prototype_change_record_extractor.py`. 대상: `data/snapshots/2026-06-official-updates/processed_md`(2026-06 staged corpus 8개 문서). 기존 hand-authored 기준: `data/snapshots/2026-06-official-updates/structured/change_records.json`(5건).

## 방법: 3가지 패턴 휴리스틱

원본 markdown을 직접 읽어보면 변경점이 최소 3가지 서로 다른 형태로 쓰여 있다.

1. **화살표 불릿**: `프라임 스텔라 10개 → 재료를 소모하지 않음` 처럼 `-?(before) → (after)` 형태. 정규식으로 바로 추출 가능.
2. **서술형 추가/제거 문장**: `아라드 나침반 - 수령 가능한 보상이 있다면, 일괄 획득할 수 있도록 '모두 받기' 버튼이 추가됩니다.` 처럼 `주어 - 내용이 추가/제거/삭제됩니다` 형태.
3. **변경 전/변경 후 표**: HTML 표가 markdown으로 변환되면서 "변경 전" 칼럼 전체와 "변경 후" 칼럼 전체가 순서대로 나열되고 칼럼 경계 표시가 사라진다. `[스킬명]` 대괄호 헤더가 각 칼럼 시작에 반복되는 것을 경계 신호로 썼다.

## 결과: 5개 hand-authored record 대비 커버리지

| record | 패턴 | 자동 추출 결과 |
|---|---|---|
| 빛의 서약 확정 획득 (프라임 스텔라 10개 → 재료 소모 없음) | 화살표 불릿 | **완전 일치.** before/after 값이 정확히 같다 |
| 아라드 나침반 '모두 받기' 버튼 추가 | 서술형 추가 | **일치.** subject/detail/change_type 모두 정확히 잡음 |
| GBL 연구소 보유 세트/서약 서비스 제거 | (해당 없음) | **놓침.** 원문 문장에 "주어 - 내용" 사이 대시가 없어서(`무기고 조회 서비스 추가에 따라 기존 GBL 연구소의 보유 세트와 보유 서약 서비스가 제거됩니다`) 서술형 정규식이 매칭되지 않았다 |
| 브레이커 질풍/타이드 바운드 쿨타임 12초→9초 | 변경 전/후 블록 | **부분 성공.** before/after 블록 분리는 됐지만 markdown 강조 표시 때문에 "기본 쿨타임"/"9초"/"로 변경"이 별도 줄로 쪼개져 후처리 없이는 값이 지저분하다 |
| 브레이커 격랑/훅 샷 공격력 15.8%→17.6% | 변경 전/후 블록 | **부정확.** 이 블록에는 대괄호 헤더가 4번(양쪽에 [타이드 바운드]와 [훅 샷] 각각) 나와서, "첫 두 번째 대괄호로 경계를 나눈다"는 단순 규칙이 깨졌다. before/after 텍스트가 뒤섞여 나왔다 |

**요약: 5건 중 2건은 완전 자동 복원, 1건은 후처리가 필요한 수준으로 부분 복원, 1건은 부정확, 1건은 완전히 놓쳤다.** 이건 "자동 추출이 다 됐다"고 주장할 수준이 아니라, 패턴별로 난이도가 다르다는 것을 보여주는 정직한 결과다.

## 예상 밖의 수확: `change_records.json` coverage gap을 드러냄 (단, 주의 필요)

이 프로토타입은 5건과 비교하려고 만들었는데, 화살표/서술형 패턴만으로 원본 8개 문서에서 **35건의 후보를 찾았다.** 그중 `'보이드 소울 2개(초월의 의지)' 물품 판매 가격이 조정됩니다`: **초월의 의지 50개 → 25개** (DNF-2927810) 건을 처음엔 "hand-authored set에 전혀 없던 발견"이라고 썼는데, 이건 부정확했다.

**정정**: 이 가격 변경은 `data/snapshots/2026-06-official-updates/structured/change_records.json`(5건, patch-note 스킬/시스템 변경용)에는 없지만, **같은 폴더의 `shop_items.json`에 `DNF-2927810-SHOP-02` record로 이미 들어 있다**(`change_type: "price_adjustment"`, `price_text: "초월의 의지 50개 → 초월의 의지 25개"`). 즉 이 프로젝트의 structured data 전체 기준으로는 이미 커버된 항목이다.

정확한 결론은 이렇다: 이 extractor는 "hand-authoring이 뭔가를 완전히 놓쳤다"를 증명한 게 아니라, **`change_records.json`이라는 좁은 스키마(패치노트 스킬/시스템 변경 5건)와 `shop_items.json`이라는 별도 스키마(상점 가격/제한 변경)가 나뉘어 있어서, 패치노트 원문을 화살표 패턴 하나로 훑으면 두 스키마의 대상이 구분 없이 섞여 나온다**는 것을 보여줬다. 여전히 유효한 발견 두 가지는 남는다.

- 몬스터 개명(`로즈베리론 → 청면수라 로즈베리론` 등)과 아바타명 띄어쓰기 수정 7건(DNF-2927522)은 `change_records.json`에도 `shop_items.json`에도 없는, 순수하게 새로 찾은 후보다(다만 QA에 중요한 변경인지는 사람 판단이 필요하다 — 오탈자 수정은 우선순위가 낮을 수 있다).
- extractor가 스키마 경계를 모르고 전부 하나의 리스트로 쏟아낸다는 것 자체가 실전 적용 전에 "이 후보가 change_records용인지 shop_items용인지 다른 신규 스키마가 필요한지" 분류하는 단계가 필요함을 보여준다.

## 한계

- 정규식 3종은 이번 8개 문서에서 관찰된 패턴에 맞춘 것이라 다른 문서/이벤트 공지에서는 실패율이 더 높을 수 있다.
- "변경 전/후" 표 패턴은 중첩된 대괄호 섹션(스킬이 2개 이상 언급되는 경우) 앞에서 깨진다. 최소 개선은 "모든 대괄호 헤더를 찾아 짝을 맞추고, 짝 사이 구간만 블록으로 삼는다"는 규칙으로 바꾸는 것이다.
- 서술형 패턴은 "주어 - 내용" 형태(대시 포함)만 잡는다. 대시 없는 평서문(예: GBL 연구소 사례)은 별도 규칙이 필요하다.
- 이 프로토타입은 추출된 항목이 사실인지 사람이 검증하지 않았다. 프로덕션에 넣기 전에는 반드시 사람 검수 단계가 필요하다.
- 이번 프로토타입은 hand-authored 5건과의 커버리지 비교가 목적이라 자동 추출 결과를 아직 RAG context builder에 연결하지 않았다.

## 결론 및 다음 단계

- 완전 자동화는 아직 멀었지만("2/5 완전 성공"), 화살표·서술형 패턴은 프로덕션 후보로 쓸 만큼 깨끗하다.
- 표 기반 패턴은 대괄호 페어링 로직을 다시 짜야 한다.
- **정정된 결론**: 가격 변경(보이드 소울)은 이미 `shop_items.json`에 있었으므로 "hand-authoring이 통째로 놓쳤다"는 처음 주장은 취소한다. 다만 몬스터 개명·아바타명 오탈자 수정처럼 어느 스키마에도 없는 진짜 신규 후보는 여전히 나왔고, extractor가 스키마 구분 없이 후보를 쏟아낸다는 한계도 확인했다. 다음 단계는 "추출 정확도를 100%로 만드는 것"보다 "화살표/서술형 패턴으로 자동 후보를 만들고, 어느 스키마(change_records/shop_items/신규)에 속하는지 사람이 분류·승인하는 반자동 파이프라인"이 더 실용적이다.
